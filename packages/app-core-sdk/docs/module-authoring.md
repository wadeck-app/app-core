# Authoring an app-module

Full reference for packages built on `@wadeck-app/app-core-sdk`. Dark-theme rules for views are in the [README](../README.md#dark-theme).

A complete, tested reference module to copy from: `packages/test-app-modules/app-module-example` (in the app-core repo), see its README.

Contents: [Start here](#start-here-the-5-minute-path) - [Layout and workflow](#layout-and-workflow) - [Migrating an existing module](#migrating-an-existing-module-to-the-new-layout) - [Troubleshooting](#troubleshooting) - [Current limitations](#current-limitations).

## Start here: the 5-minute path

Install the CLI once: `npm install -g @wadeck-app/app-core-cli`.

1. **Create.** `app-core-cli init ./app-module-<name> [--id <id>] [--title "Display name"]` writes the smallest module below (it refuses a folder that already has content), and it passes `check` as is. Or **copy** `packages/test-app-modules/app-module-example` into your repo as `app-module-<name>` (the comments in its sources say why each line exists). It requires the `slot-provider` fixture; for a first module drop `requires`, `expose` and the contribution to `slot-provider:shared-slot` from `manifest.json`, or start from this smallest module (checked and packaged with the built CLI):

   ```
   app-module-mini/
     manifest.json            {"id":"mini","extensionPoints":[{"kind":"page","slot":"nav","label":"Mini","view":{"type":"path","value":"./src/dsl-views/page.yaml"}}]}
     package.json             {"name":"app-module-mini","version":"0.0.0","files":["dist-module"]}
     .gitignore               dist-module, .app-core-dev
     src/dsl-views/page.yaml  $type: Badge / label: hello
     src/backend/index.ts     export default (ctx) => { ctx.registerRoute('GET', '/ping', (_req, reply) => reply.send({ ok: true })); }
   ```

2. **Set your identity.** `id` in `manifest.json` (letters, digits, `_`, `-`); it prefixes your routes (`/api/modules/<id>/...`) and components (`<id>:Name`).
3. **Check.** `app-core-cli check ./app-module-<name>` writes nothing and lists every layout or manifest problem with its fix. Add `--link <package>=<folder>` for providers not installed in `node_modules`.
4. **Run it.** `app-core-cli dev ./app-module-<name> --watch` starts a real app-core with your module (and the modules it `requires`), prints the URL, and rebuilds on every change under `src/` and `manifest.json`.
5. **Package.** `BUNDLE_VERSION=<version> app-core-cli package ./app-module-<name>` writes `dist-module/`.
6. **Publish** the package (`npm publish` ships only `dist-module`): run step 5 in CI first.
7. **Register** from your daemon with the [SDK `register` subpath](registering-a-module.md): `registerModule({ id, manifestPath: '<install dir>/dist-module/manifest.json' })`. The `id` must equal the manifest's.

Anything fails: see [Troubleshooting](#troubleshooting).

## Layout and workflow

An app-module is a package named `app-module-<name>` (e.g. `app-module-queue`):

```
app-module-<name>/
  manifest.json              source manifest: id, extensionPoints, dslLib.shared
  package.json               "files": ["dist-module"]
  .gitignore                 dist-module
  src/
    backend/index.ts         backend entry (fixed name): default export (ctx) => void
    dsl-views/*.yaml         views referenced by path-type extensionPoints
    dsl-components/index.ts  optional dsl-lib components (React); style.css next to it
    commons/                 code shared by backend and dsl-components
  dist-module/               generated by `package`, gitignored
```

Rules, all enforced by `app-core-cli check`:

| Rule | Detail |
|---|---|
| Root | Only `src`, `dist-module`, `node_modules`, dot folders, `manifest.json`, package/lock files, `README*`, `LICENSE*`, `CHANGELOG*`, `tsconfig*.json`, `*.config.*`. |
| `src` | Only `backend`, `dsl-views`, `dsl-components`, `commons`; no loose files. |
| `dsl-views` | `.yaml`, `.yml`, `.json` only. |
| React / JSX | `.tsx`/`.jsx` files and `react`/`react-dom` imports only in `dsl-components`. |
| `commons` | No `node:` or Node builtin imports (it is shared with the browser); imports neither `backend` nor `dsl-components`. |
| `backend` / `dsl-components` | Never import each other; share through `commons`. |
| Backend entry | `src/backend/index.ts`, with a default export. |
| Publishing | `.gitignore` lists `dist-module`; `package.json` `"files"` is exactly `["dist-module"]`. |

`check` also validates the manifest and that every referenced view exists. Each error names the file and the fix, and all problems are listed in one run.

In this repo the same layout rules also run as `violations` rules (`app-module/*`, scoped to any `app-module-*` folder, with a parity test against `check`). Other repos rely on `check`; the rules do not apply there on their own.

```sh
app-core-cli check ./app-module-queue                  # layout + manifest, writes nothing
BUNDLE_VERSION=2026.10.18-001 app-core-cli package ./app-module-queue
app-core-cli dev ./app-module-queue --watch            # real app-core with your module and its dependencies, rebuilt on change
npm publish                                            # ships dist-module only
```

### `package`

`app-core-cli package <module-dir> [--out <dir>] [--version <v>] [--link <package>=<folder>]...` runs `check`, then rebuilds the output folder from scratch (default `<module-dir>/dist-module`, emptied first; it refuses the module folder, its parents and `src/`). The version comes from `--version`, else `BUNDLE_VERSION`; with neither it fails (no default). Unknown flags fail.

| Part | Output |
|---|---|
| Backend | `api-backend/backend.cjs` + `.cjs.map`: esbuild bundle, tree-shaken, not minified (readable production stack traces; the sourcemap maps to `src/`). |
| Lifecycle hooks | Each declared hook gets the same bundle and footer: `api-backend/teardown.cjs`, `api-backend/migrate.cjs` (+ maps). |
| dsl-lib | `dsl-lib/entries.mjs` from `src/dsl-components/index.ts`: tree-shaken, minified, shared singletons external. Only when the manifest has `dslLib`. |
| CSS | `src/dsl-components/style.css` copied as built to `dsl-lib/style.css`. No CSS tool runs: build it with Tailwind first (see dsl-lib below). |
| Views | Only views the manifest references: parsed, validated, written as compact JSON to `dsl-frontend/`. Other files in `src/dsl-views` are not packaged and are reported as warnings. |
| Manifest | `manifest.json` with `version` stamped and `backendEntryPath`, `dslLib.entry`/`css` and view paths pointing at the outputs above. |

The written manifest is then parsed with the server's schema, and every path it names must exist inside the output.

### Source manifest and packaged manifest

You write the source manifest; app-core loads the packaged one.

| Field | `manifest.json` (source) | `dist-module/manifest.json` |
|---|---|---|
| `id` | required | copied |
| `version` | not allowed | stamped by `package` |
| `backendEntryPath` | not allowed (the entry is always `src/backend/index.ts`) | `./api-backend/backend.cjs` |
| Path views | `./src/dsl-views/<file>.yaml` | `./dsl-frontend/<file>.json` |
| `dslLib` | `{ "shared": { ... } }` | adds `entry` and `css` |
| `requires` | optional | copied |
| `optionalRequires` | optional; same shape as `requires`, an id is in one of the two | copied (see [Contributing to a module you can do without](#contributing-to-a-module-you-can-do-without-optionalrequires)) |
| `expose` | optional; `types` is `./src/commons/<file>.ts` | `types` becomes `./types/index.d.ts` |
| `lifecycle` | optional; `teardown` / `migrate` are `./src/backend/<file>.ts` | `./api-backend/teardown.cjs` / `./api-backend/migrate.cjs` |
| `showInNav` | optional boolean, `true` when absent | copied |
| `title` | optional non-blank string | copied |

The source manifest is strict: any other field fails `check`.

**Validating a manifest from another tool.** The SDK main entry exports the schemas app-core and `check` apply: `import { parseSourceManifest, SourceManifestSchema, ManifestSchema } from '@wadeck-app/app-core-sdk'`. `SourceManifestSchema.safeParse(json)` returns every problem as an issue with a `path` and a `message` (the cross-field rules included: menu pages, widget sizes, reserved names). The entry depends on `zod` only (no Node module, no server), and the schemas are part of the SDK's public surface: a rule is added or tightened with the release that ships it. Do not copy the rules by hand.

**Checking the manifest with `violations`.** Nothing to set up: when a project has an `app-module-<name>/manifest.json`, the `violations` runner loads the rule `app-core-sdk/manifest-valid` from the project's own `@wadeck-app/app-core-sdk` (the version the module is built against, so it follows `npm update @wadeck-app/app-core-sdk`) and reports, for every `manifest.json` that declares `extensionPoints`, the same problems as `app-core-cli check`. It says `[auto] app-module-* detected` when it does. If the SDK is not installed or too old, the runner fails with the command to run. Turn it off with `'@wadeck-app/app-core-sdk/violations': { $severity: false }` in `.violations/config.ts`. A project without `violations` is covered by `app-core-cli check`.

**Display name.** `"title": "Flow charts"` is the name the shell shows (top-bar tab, side-menu heading, dashboard shortcut, and the two letters of the logo). Without it the shell derives one from the id (`flow-chart` becomes "Flow chart"). A blank title fails `check` and `package`.

**Keeping a module out of the navigation.** `"showInNav": false` removes the module from the shell's navigation: no tab in the top bar and no shortcut on the dashboard menu. The module is still loaded and its pages stay routable (reachable by link); while one of them is open, the side menu lists the module's pages. A module without any `page` / `nav` extension point (widgets only) is never listed, with or without this field, so use `showInNav: false` for a module that has `nav` pages you do not want in the menu. The value must be a boolean: `"false"` (a string) fails `check` and `package`.

### manifest.json

```json
{
  "id": "my-module",
  "extensionPoints": [
    {
      "kind": "page",
      "slot": "nav",
      "label": "My Module",
      "view": { "type": "path", "value": "./src/dsl-views/page.yaml" }
    }
  ]
}
```

- `id` is required: it is the module's identity, the prefix of its components (`<id>:Name`) and routes. Same charset as registration ids (below). Registration must use this id; a different one is refused.
- Every `view` of `type: "path"` must be a file inside `src/dsl-views/`.
- `view` can also be `{ "type": "inline", "value": { "$type": "Badge", "label": "..." } }` for a
  widget simple enough not to need its own file.
- `extensionPoints[].kind` is `"widget"` (renders into app-core's dashboard grid) or `"page"`
  (renders into app-core's top navbar, routed to a full page). `slot` is `"dashboard"` or
  `"nav"` respectively.
- `extensionPoints[].path` (optional, pages only, e.g. `"/jobs/:id"`): mounts the page at
  `/modules/<moduleId><path>` as its own route; `:name` segments reach the view as `$route.name`.
  Segments are letters, digits, `_` or `-`; no `..`, no trailing slash. The path `"/"` alone is the
  module's home page, mounted at `/modules/<moduleId>` (with or without a trailing slash).
- `slot: "route"` (with `kind: "page"`): the page is reachable only by link, not listed in the
  navbar (detail, edit and log pages). Link to it from another view with dsl-ui `Link`/`ButtonLink`
  (`href: /modules/<moduleId>/jobs/...`). Routes disappear when the module is unloaded or swapped.
- `dslLib` (optional): runtime-loaded components, see "Shipping components (dsl-lib)" below.
- `lifecycle` (optional): `{ "teardown": "./src/backend/teardown.ts", "migrate": "./src/backend/migrate.ts" }`, see "Lifecycle hooks" below.
- `extensionPoints[].order` (optional number) only matters if your module contributes to another
  module's `ExtensionSlot` -- app-core sorts by it and strips it before rendering; it's a purely
  structural sort key, app-core never interprets what it means.

To validate a single manifest against the server schema, run `app-core-cli validate <manifest.json>` on the packaged `dist-module/manifest.json`. The source manifest has no `version` or `backendEntryPath`, so `validate` rejects it: use `check` for it.

### Registering the module with app-core

A daemon pushes a registration to app-core's own server, pointing at the packaged manifest:

```sh
curl -X POST http://127.0.0.1:4850/api/modules/register \
  -H 'Content-Type: application/json' \
  -d '{"id": "my-module", "source": {"type": "file", "path": "/absolute/path/to/dist-module/manifest.json"}}'
```

The registered `id` must equal the manifest's `id`: `register` answers `400` otherwise, and a registry entry that mismatches lands in `failed` at load. A `path` that does not exist answers `400` naming the path. The SDK helper is described in [registering-a-module.md](registering-a-module.md).

`register` and `update` answer `{ id, version, extensionPoints, cascaded, recovered }` (plus `held`, below): `cascaded` lists the modules unloaded because of this change, `recovered` the failed modules loaded again because of it (see [Providers and dependents](#providers-and-dependents)). Both are also present on failure answers.

**Memory on update.** An update lets go of the previous copy of a CommonJS backend and hooks (`.cjs`, what `package` writes): the memory of the server does not grow with the number of updates (12 updates of an 8 MB backend: no more than a few copies, not twelve). An ES module (`.mjs`) cannot be unloaded by Node: each update keeps the previous copy until the server restarts, and the answer says so in `held` (a list of messages naming the file; absent when nothing is kept). Ship the `.cjs` that `package` writes. Only the module's own files are let go of: a `.cjs` that `require`s other files at run time (a bundle does not) leaves those in Node's cache.

What a rejected registration leaves behind (`retained` in the answer, with a sentence saying so):

| Rejection | Registry entry | `retained` |
|---|---|---|
| A required module is missing or does not fit, module not running | kept; the module is `failed` (cause `requirement`) and loads by itself when the requirement is met | `true` |
| Refused before anything changed (invalid manifest, id mismatch, missing file, bad dsl-lib) | a new module leaves none; an existing one keeps its entry and its running version | `false` |
| An update of a running module that needs a missing module | unchanged; the running version keeps serving | `false` |
| The old version was torn down and the new one did not start (migrate/setup threw) | kept; the module is `failed` (cause `error`), not retried automatically | `true` |

Use `/api/modules/update` instead of `/register` once the module is already known, to push a new
version live with no app-core restart (the backend is reloaded when its file changed, even under an
unchanged `version`; bump `version` anyway so the change is visible). If app-core is unreachable, write the same JSON body
directly to `<app-core-config-dir>/modules/<id>.json` instead -- app-core picks it up on its own
next startup. `id` must be a fixed literal string your daemon controls, never derived from
untrusted input.

### Publishing

Publish `dist-module` as a folder, not a zip: an npm tarball is already an archive. Run `package` in CI (with `BUNDLE_VERSION`) right before `npm publish`; `check` guards `.gitignore` and `"files"`.

### `dev`

`app-core-cli dev <module-dir> [--port <n>] [--watch [--poll]] [--reset] [--ab-tests] [--previous-version <v>] [--link <package>=<folder>]... [--id <id>]` starts a real app-core (config dir `<module-dir>/.app-core-dev`, bundled dashboard) with the module and everything it requires, then prints each module (id, version, origin) and the URL.

- **Source module** (has `src/`): `check` runs first and fails with its normal messages, then the same pipeline as `package` writes `<module-dir>/dist-module` with version `0.0.0-dev` (always this version, printed) and registers it.
- **Built module** (a `dist-module` folder or its `manifest.json`): registered as is; `--watch` is refused. A manifest that is neither (no `backendEntryPath`, no `src/`) is an error telling you to run `package`.
- **Dependencies**: each id in `requires` is resolved to a built package the way `check` finds providers (a `package.json` dependency in `node_modules` whose `dist-module/manifest.json` has that id; `--link <package>=<folder>` overrides it), recursively from each dependency's own folder, each id once (first location wins). Their `dist-module` manifests are registered; the server loads them in `requires` order. Nothing starts when an id has no built package (the error names the id, who requires it, where it looked, and says install / build / `--link`), when a dependency is only a source module (build it yourself: `dev` never packages modules you do not develop), or on a require cycle (the error shows the cycle).
- **`--watch`**: `src/` and `manifest.json` of the module under development are watched (`fs.watch` recursive, 200 ms debounce; where recursive watch is unavailable, or with `--poll`, mtimes are polled every 500 ms and the banner says so). Each change runs `check` + `package` and pushes the result through the server's own `POST /api/modules/update`; one line per rebuild: `ok` with its duration, or the full error. A failed rebuild exits nothing: the previous version keeps serving (if the update fails after the old version's teardown, the server message says the module is failed until the next good build). Rebuilds run one at a time; changes during a rebuild queue exactly one more. Dependencies are not watched: rebuild one and restart `dev`.
- **Config dir**: `<module-dir>/.app-core-dev/` (for a built `dist-module`, the folder that holds it), kept between runs: `data/` (`ctx.dataDir`) and `state/` (the persisted previous version) survive, for the module and its dependencies alike. Only the registry (`modules/`) is rewritten at each start. Add `.app-core-dev` to `.gitignore`; `check` accepts it and `package` never copies it.
- **`--reset`**: wipes `.app-core-dev` before starting (banner line `--reset: wiped ...`). If the wipe fails, the error names the folder.
- **`--ab-tests`**: shows the A/B test dock (`AbTest` nodes of your views) in the bundled dashboard, which hides it otherwise.
- **`--previous-version <v>`**: writes `<v>` as the module's last loaded version before the start, so `migrate` runs with it as `previousVersion`. Without it, a second run is the same version (`0.0.0-dev`) and `migrate` does not run. `<v>` equal to the version dev loads is an error (migrate would not run).
- **Stop**: SIGINT/SIGTERM close the server, so module teardowns run (reason `shutdown`); the config dir is kept.
- The id comes from the manifest; `--id` only asserts it. A manifest without `id` is an error. A dependency or (without `--watch`) the module itself that fails to load makes `dev` exit with the reason.
- A failed rebuild after `check` passed can leave `dist-module` incomplete (it is rewritten in place); fix the source and the next rebuild restores it.

### Module ids, load failures and removal

- The module `id` must match `^[A-Za-z0-9][A-Za-z0-9_-]*$` (letters, digits, `_`, `-`); anything else is rejected with `400`.
- A registered module that cannot load (missing or invalid manifest, manifest `id` different from the registered one, backend or a hook throws, times out, or has no function default export) does not stop app-core. It is listed under `failed` in `GET /api/modules` (`id`, `source`, `error`, `failedAt`, `cause`), printed on stderr at startup, and shown as an alert in the UI. Fix it and re-register, or remove it.
- When your daemon is uninstalled, unregister the module so it does not come back on restart:

```sh
curl -X POST http://127.0.0.1:4850/api/modules/unregister \
  -H 'Content-Type: application/json' -d '{"id": "my-module"}'
```

`200 { "id": "my-module", "removed": true, "cascaded": [...], "recovered": [...] }`; `404` if app-core does not know the id. The modules that require it are unloaded first and stay registered, see [Providers and dependents](#providers-and-dependents).

### The backend entry

`src/backend/index.ts` has a single default export: a function receiving
`ModuleContext` (typed by this package). `package` bundles it into the file app-core loads. If the loaded default export is not a function, the module fails to load (listed in `failed`, the message says how to fix it); it is no longer skipped silently.

```ts
import type { ModuleContext } from '@wadeck-app/app-core-sdk';

export default function (ctx: ModuleContext) {
  // Register an HTTP route under /api/modules/<your-module-id>/history --
  // app-core enforces the id prefix itself, you only give the sub-path.
  ctx.registerRoute('GET', '/history', (_req, reply) => {
    return reply.code(200).send({ entries: ['...'] });
  });

  // Scoped timers/listeners -- use these, never raw setInterval/setTimeout/
  // addEventListener. app-core clears everything registered here automatically
  // when your module is unloaded or swapped to a new version.
  ctx.setInterval(() => {
    // periodic background work
  }, 30_000);
}
```

`ModuleContext` (typed by this package):

| Member | Notes |
|---|---|
| `dataDir` | Persistent folder of the module. |
| `registerRoute(method, subPath, handler)` | Cleared on unload. |
| `fileVersion(...files)`, `unchanged(req, reply, version)` | Answer 304 without computing: see [Data that changes rarely](#data-that-changes-rarely-etag-and-304). |
| `setInterval(fn, ms)`, `setTimeout(fn, ms)` | Return an opaque `ModuleTimerHandle`; keeping it is optional, everything still running is cleared on unload. A fired timeout is dropped from tracking. |
| `clearInterval(handle)`, `clearTimeout(handle)` | Stop one timer. Already cleared, already fired, or after unload: no-op. A value that is not a handle, or the other kind of handle, throws and says what to pass. |
| `on(event, fn)`, `off(event, fn)`, `emit(event, ...args)` | `off` of an unknown listener, or after unload: no-op. |

Because timers and listeners can be released one by one, creating them per request is fine as long as you release them (the example registers a `tick` listener per SSE stream and calls `ctx.off` when the stream closes).

The function may return the module's running state (or a promise of it): app-core keeps it and gives it to `teardown` as `ctx.instance` (see [Lifecycle hooks](#lifecycle-hooks-previous-version-and-datadir)). Type it with `ModuleSetup<MyInstance>`.

Raw `setInterval`/`setTimeout`/`addEventListener` in `src/backend` are rejected by a `violations` rule (`app-module/no-raw-timers`) in this repo; in other repos it is on you.

#### Streaming responses (SSE)

A handler may stream: call `reply.hijack()`, then write to `reply.raw` (`writeHead(200, { 'Content-Type':
'text/event-stream' })`, `write('data: ...\n\n')`). Clean up in `req.raw.on('close', ...)`.

When your module is unloaded, swapped by an update or unregistered, app-core ends the streams it
already started (headers sent, not finished): your `close` handler runs and the client reconnects
(`EventSource` does it by itself) to the new version. Requests still waiting for their handler are not
touched.

#### Route parameters

A sub path may contain `:name` segments. The handler reads them from `req.params`, which holds only
your own parameters (a parameter may be called `id`):

```ts
ctx.registerRoute('POST', '/dlq/:id/replay', (req, reply) => reply.send({ replayed: req.params.id }));
```

- Matching is per segment, on method and segment count; static segments win over parameters
  (`/jobs/new` before `/jobs/:id`).
- Values are URL-decoded. A malformed encoding answers 404.
- Two routes of the same method and shape (`/a/:x` and `/a/:y`) cannot both be registered:
  `registerRoute` throws, and the module is reported in `failed` instead of silently overwriting one.
- Names must be letters, digits or `_`; the sub path `/_lib` is reserved (see dsl-lib below).

### Lifecycle hooks, previous version and `dataDir`

Each hook is its own file under `src/backend` whose default export is the function; `check` verifies the file exists and has a default export, `package` bundles it.

```ts
import type { ModuleHookContext, ModuleTeardownContext } from '@wadeck-app/app-core-sdk';

// migrate: ctx = { id, version, previousVersion: string | null, dataDir }
export default async function migrate(ctx: ModuleHookContext) {}

// teardown: the same fields plus reason and instance
export default async function teardown(ctx: ModuleTeardownContext<MyInstance>) {}
```

| Hook | Runs | `ctx.version` |
|---|---|---|
| `teardown` | When this instance is replaced by an update, unloaded, unregistered, torn down because a module it requires went away, or the server shuts down. | the version being stopped |
| `migrate` | When a version loads and `previousVersion` is non-null and different from it. Never on first install or a same-version reload. | the version being loaded |

- `previousVersion` is the last version that loaded successfully, kept in `<config dir>/state/<id>.json` after each successful setup. `null` on first install. A restart is not an update (same version, no migrate). Unregister clears it, so a reinstall is a first install. A state file that cannot be parsed fails the load, naming the file: restore `{"version":"<last>"}` or delete it.
- `ctx.dataDir` (also `ModuleContext.dataDir`, so `setup` has it too) is `<config dir>/data/<id>/`, created before any hook runs. Keep your persistent data there. **app-core never deletes it**, not even on unregister. A module that wants its data gone on uninstall deletes it in `teardown` when `ctx.reason === 'unregister'`; otherwise remove it by hand.
- `teardown` also receives:

  | Field | Value |
  |---|---|
  | `reason` | `'update'` (a new version replaces this one), `'unregister'`, `'unload'` (unloaded, not unregistered), `'shutdown'`, `'dependency'` (a module it requires was unregistered, failed or changed incompatibly) |
  | `instance` | What the backend's default export returned (awaited), the very same object; `undefined` if it returned nothing. `migrate` runs before setup and gets neither field. On an update the old teardown gets the OLD instance. |

  Keep the state in the returned object and flush it in `teardown`; no need to save it continuously.
- Load order on a load or update:
  1. pre-checks (manifest, views, `requires`, state file) and import of the new backend and hooks: no side effects, a failure here leaves the running instance serving;
  2. `teardown` of the old instance (its own context, with the version it was loaded with), then its context is disposed;
  3. `migrate` of the new instance;
  4. setup (the default export of the backend);
  5. the new version is persisted.
- A failure at step 3 or 4 puts the module in `failed` with the reason. **There is no rollback**: the old instance was torn down and is not restored. Everything the new setup registered before failing (routes, timers, listeners) is disposed. `migrate` runs again on the next load until it succeeds, so write it to be safe to run twice.
- Import, setup and each hook have a timeout: 30 s, or `APP_CORE_HOOK_TIMEOUT_MS` (positive integer in ms; anything else stops app-core at startup). A timed-out step is reported as an error naming the module and the hook, but a JavaScript promise cannot be cancelled: the code keeps running in the background.
- Teardown errors and timeouts are written to stderr (module id, hook, message) and never stop the unload or the update.
- Shutdown tears modules down level by level: the modules nobody requires first, all of one level at the same time, each under its own timeout, then the modules they required. Two slow hooks of one level take about the longer one, not the sum.
- Loads, unloads and unregisters of one id are serialized.

### Live data in a view (`$sources`)

A view can fetch live data from a route your own backend registered:

```yaml
# src/dsl-views/page.yaml
$sources:
  history:
    url: GET /api/modules/my-module/history

$type: DataTable
rows: $sources.history.entries
```

The URL in `$sources` is a plain string handed to app-core's frontend `fetcher` -- same-origin,
no base-path logic to worry about. Keep the module id a fixed literal in the URL (as shown), never
a `$route`/dynamic placeholder -- an empty-placeholder path silently skips the fetch in the
underlying DSL renderer, so a fixed literal is the safe pattern.

### Data that changes rarely (ETag and 304)

A view that refreshes a source (`poll`, a refresh button) asks the same route again. Two things keep an unchanged answer cheap:

- **Automatic.** Every 200 answer to a GET route whose body is text (JSON included) gets an `ETag` (a hash of the body) and `Cache-Control: no-cache`. The browser sends the tag back (`If-None-Match`) and the server answers 304 with no body when it is the same. Only the bytes are saved: your handler still runs. A route that sets its own `ETag` or `Cache-Control` keeps them. Streams and other methods are left alone.
- **Ahead of the work.** When your data is kept in files, say so and skip the computation:

```ts
ctx.registerRoute('GET', '/report', async (req, reply) => {
  // 304 if report.json and rules.json are as the client last saw them; the report is not rebuilt.
  if (ctx.unchanged(req, reply, await ctx.fileVersion(reportFile, rulesFile))) return reply;
  return reply.send(await buildReport());
});
```

`fileVersion` changes when a file is modified (time or size) or appears or disappears; a missing file is a version, not an error. `unchanged` takes any text that changes when the answer would (a revision number, a counter), not only a file version. It sets the `ETag`; when the client has that version it answers 304 and returns `true`, and the handler must return the reply and do nothing else. Both are for GET routes.

How often a view refreshes is the view's `poll` (`$sources.<key>.poll: 30s`): a `poll` reloads every source of the page at each tick, so a route that cannot change that often is better behind `unchanged`.

### Pages below pages (the breadcrumb)

The shell shows the trail of nested pages above every module page: the module, then every page of the module whose `path` is the start of the current address, each linking to its page. For `/tasks/7/history` with pages `/tasks`, `/tasks/:id` and `/tasks/:id/history`: Task > Tasks > Task 7 > Task history. A page needs no "back" button: the crumb before it is the way back.

- Give every page a `label`. A page without one is named after its address ("Execution" for `/executions/:id`), which is rarely what you would write.
- A page whose address ends with a parameter shows its value after the label ("Task 7"; a long value is shortened).
- The module home (`"path": "/"`) is the parent of the pages no other menu page claims (a route like `/jobs/:id` under the home page "Jobs"); it does not appear before `/schedule`, which is a menu page of its own.
- A page declared without a `path` (addressed by its index) has no pages below it in the trail.
- A menu page is named in the trail like in the menu: the module name in front of its label is dropped ("Flow Executions" under Flow reads "Executions").

### Sizing a dashboard widget (`width`, `height`)

A `widget` on slot `dashboard` may say how many cells of the dashboard grid it takes. The grid has 4 columns on a wide screen, 2 on a medium one and 1 on a narrow one; a widget wider than the columns available takes them all.

```json
{ "kind": "widget", "slot": "dashboard", "label": "Runs per day", "width": 2, "height": 2, "view": { "type": "path", "value": "./src/dsl-views/runs.yaml" } }
```

- The dashboard is a lattice of square cells of 100px (16px apart, about 10 columns on a wide screen). `width`: 1 to 12 cells; without it a widget takes 3 and more when its content is wider than its tile (a row of figures that would be cut), up to the columns that exist; a declared width is kept as it is. `height`: 1 to 12 cells, default 1. A height is a minimum: a widget whose content needs more room takes more whole cells, so a widget never scrolls inside or gets cut.
- Anything else (0, 5, 1.5, a string) fails `check` and `package`, and so does a size on a widget that is not on the dashboard slot, where it would have no effect.

### Feedback of user actions (`$actions`)

The shell shows the outcome of every action of a view (row and batch actions, forms, brains) as a toast; you write no code for it.

- A failure always shows: `Action "<name>" failed (HTTP <status>): <server message>`. The message is the `message` (else `error`) of your route's JSON answer, so make it say what to do. Error toasts stay until dismissed.
- A success shows only when the action declares `successMessage`. Add `errorPrefix` to put your own words in front of the server message.

```yaml
$actions:
  replay: { url: "POST /api/modules/queue/jobs/{id}/replay", successMessage: "Job queued again", errorPrefix: "Could not replay" }
```

### Navbar and overlay widgets

Two more widget slots exist for things that live outside any page:

```json
{ "kind": "widget", "slot": "navbar", "order": 1, "view": { "type": "path", "value": "./src/dsl-views/stats.yaml" } },
{ "kind": "widget", "slot": "overlay", "view": { "type": "path", "value": "./src/dsl-views/failures.yaml" } }
```

- `navbar`: rendered inline on the right of the navbar, before the theme toggle, on every page. Keep it
  compact; entries are sorted by `order` (none last), then module order.
- `overlay`: mounted once on every page, at the app root. The shell gives no position: your component
  places itself (e.g. `position: fixed`, bottom-right). The shell does not manage position or z-index
  between modules. Measured with two modules that both pin a box to the bottom-right: both are mounted
  and they sit exactly on top of each other, the later module's box hiding the other, so nobody sees
  that two overlays exist. Pick a corner or an offset unlikely to be shared, a modest `z-index`, and keep
  a small footprint. Colors must come from theme tokens (`var(--color-surface)`, `var(--color-content)`,
  `var(--color-border)`), not fixed values: a fixed dark text was unreadable in the dark theme.
- Both are DSL views like dashboard widgets (`$sources` and `dsl-lib` components work), shown only once
  your components are loaded, and removed when the module is unloaded or swapped.
- Each widget has its own error boundary: if a component throws, the shell shows `<moduleId>: widget error`
  (inline in the navbar, bottom-left for an overlay), logs the error with `console.error` naming your
  module, and keeps the page and other widgets working. The notice resets when the view or lib changes.
- They render on every page: poll sparingly and clean up timers in your components.

### Contributing into another module's slot (`ExtensionSlot`)

Slot ids are the shell slots (`dashboard`, `nav`, `route`, `navbar`, `overlay`) or `<providerId>:<slot>`; any other id is rejected by `check` and at load.

**Providing a slot.** Declare it in the source manifest; `accepts` lists the allowed root `$type`s.

```json
{ "id": "queue", "expose": { "types": "./src/commons/types.ts", "slots": { "subscriber-row": { "accepts": ["Badge", "IconButton"] } } } }
```

- Embed `{ "$type": "ExtensionSlot", "items": "$sources.<key>" }` with the source `GET /api/slots/queue:subscriber-row`.
- `expose.types` is optional: a types-only file in `src/commons` (interfaces, types, `import type`; no runtime code, no relative imports: it is copied alone). `package` writes it to `dist-module/types/index.d.ts`. `package.json` must have `"exports": { "./types": { "types": "./dist-module/types/index.d.ts" } }`.

**Contributing.** Add the provider to `package.json` dependencies, list it in `requires`, and use `slot: "queue:subscriber-row"`.

```json
{ "id": "billing", "requires": { "queue": "^1.0.0" }, "extensionPoints": [{ "kind": "widget", "slot": "queue:subscriber-row", "view": { "type": "path", "value": "./src/dsl-views/row.yaml" } }] }
```

`check` and `package` find the provider by reading `node_modules/<dependency>/dist-module/manifest.json` of each dependency (`dependencies`, `devDependencies`, `peerDependencies`) and matching its `id`. Where the dependency is not installed in `node_modules`, pass `--link <package>=<folder>` (folder holding its `dist-module`; repeatable, accepted by `check` and `package`). A key that is the **module id** also works (`--link task=../app-module-task`): it is used whatever `package.json` lists, which is what a provider you do not depend on (`optionalRequires`) needs, since its package name is not in your dependencies. A link that does not work (no built `dist-module`, or another module's id) is reported, never skipped. They report:

- `requires` does not list the provider, or the provider is not found, not built, or does not expose the slot;
- the ROOT `$type` of the contributed view is not in `accepts` (children are not validated).

At load, app-core applies the same rules to the modules it has loaded, plus the version: the module goes to `failed` (register answers 422) with the fix when a required module is not loaded or failed, its version is outside the `requires` range (a version that is not valid semver never matches), or the slot or `$type` is rejected. At startup modules load in `requires` order; members of a require cycle go to `failed`.

**What a contributed view reads.** The provider's page renders it with its own data: `$sources.<key>` of that page and `$route.<param>` of its address are available to the contribution (`label: $route.project`, `href: /modules/task/tasks?project=$route.project`). A `$sources` written on the contributed node itself is ignored without an error: only a page declares sources. To show data of your own module, build the view from the provider's data, or ship a `dslLib` component that fetches by itself (the provider must then list its `$type` in `accepts`). (Test: `ExtensionSlot.hostContext.test.tsx`.)

### Contributing to a module you can do without (`optionalRequires`)

`requires` is hard: without the provider the whole module is `failed`. When your module works without it and only adds something to its page when it is there, list it in `optionalRequires` (same shape as `requires`) instead:

```json
{ "id": "project", "optionalRequires": { "task": "*" }, "extensionPoints": [{ "kind": "widget", "slot": "task:project-header", "view": { "type": "inline", "value": { "$type": "Badge", "label": "Project" } } }] }
```

- The module loads whether the provider is there or not. A contribution to a provider that is not loaded is **inactive**: `GET /api/modules` gives the module a `warnings` list and the extension point an `inactive` reason, and the log says it once at load. `GET /api/slots/<slot>` and the side menus leave inactive contributions out.
- It is worked out from the modules loaded at each request, so a provider that registers or updates activates what waited for it, and one that goes away deactivates it again. **No cascade**: an optional provider leaving unloads nobody. A provider that is there but does not fit (version outside the range, slot not exposed, root `$type` not in `accepts`) gives an inactive contribution with that reason, not a failed module.
- Optional edges are not part of the load order, the cycle check or the cascade: two modules may list each other (`project` <-> `task`), each offering slots the other contributes to. A `requires` cycle is still refused.
- An id is in `requires` or in `optionalRequires`, not both, and never your own id. The range is checked like a `requires` range.
- `check` and `package` hold an optional provider that they can find (`node_modules`, `--link`) to the same rules as a required one, as errors. One they cannot find is a single warning line that gives the reason (not installed, or what is wrong with the `--link`), however many contributions it has: they are not validated, and `package` carries the warning in its result. To validate against a provider you do not depend on, `--link <module id>=<folder>`.
- Your own slots need no declaration. Declare only the modules you contribute to.

### Adding a page to another module's side menu (`<providerId>:nav`)

Every module's side menu is the slot `<id>:nav`, with nothing to declare. A module that `requires` the provider adds an entry with a `page`:

```json
{ "id": "flow-chart", "requires": { "flow": "^1.0.0" }, "extensionPoints": [{ "kind": "page", "slot": "flow:nav", "label": "Flow chart", "path": "/chart", "order": 10, "view": { "type": "path", "value": "./src/dsl-views/chart.yaml" } }] }
```

- The entry shows after the provider's own pages, sorted by `order` (none last), then module order.
- The page stays yours: it is served at `/modules/<your id><path>`. While it is open, the provider's tab, side menu and accent are active.
- Required: `kind: "page"`, a `label` (the entry text) and a fixed `path` (no `:param`). `check`, `package` and load report what is missing.
- The provider needs no `expose`, and `expose.slots` may not be named `nav` (reserved). The root `$type` is not checked.
- Like any contribution: `requires` must list the provider, and it must be found (see above). Its version must be valid semver and satisfy the range (prereleases count): `2026.10.26-278-d44c4cdd` satisfies `*` and `>=2026.10.0`. A version with a leading zero (`2026.10.05`) is not valid semver and never matches.
- A module cannot use `<own id>:nav`: use `nav` for your own pages. A module with only such pages gets no tab; the provider's tab carries them.
- When the provider is unregistered, the entry goes with it (dependents rules below).

### Separating groups in the side menu (`separatorBefore`, `groupLabel`)

A `page` of the menu (slot `nav`, or `<providerId>:nav`) can set itself apart from the entry above it:

```json
{ "kind": "page", "slot": "nav", "label": "Jobs", "path": "/jobs", "separatorBefore": true, "groupLabel": "Automation", "view": { "type": "path", "value": "./src/dsl-views/jobs.yaml" } }
```

- `separatorBefore: true` draws a rule above the entry; `groupLabel` is the caption of the group that starts there (only with `separatorBefore: true`, not empty).
- A separator that would be first or last in the menu is not drawn. In a folded or icon-only menu a caption is not shown, the rule stays.
- Both fields fail `check` and `package` on anything that is not a page of the menu, and `groupLabel` without `separatorBefore: true`, with the fix in the message.
- The menu orders entries as before (own pages in manifest order, then contributed pages by `order`), so place the entry that starts a group where you want the rule.

### Dates and times

Never format a date yourself: the shell has one formatter, set by the user (calendar-clock button in the top bar) and applied to every date, so a module that formats its own ignores the user's choices. Settings, kept in the browser: language (English `en-GB` by default, never the browser's language unless the user picks "auto"), ISO 8601 or the language's conventions, 12h/24h, time zone (computer, UTC or a name), first day of the week, weekday names.

| You write | Use |
|---|---|
| A DataTable column | `format: datetime` (or `date`, `time`), optional `dateStyle: short \| medium \| long` (default `short`). The exact instant is the cell's tooltip. |
| A date in a view | `$type: DateText` with `value`, optional `dateStyle` (default `medium`), `part: datetime \| date \| time`, `relative: true` ("5 minutes ago"). Text only; the tooltip is the exact instant. |
| A component (`dsl-lib`) | `useDateFormat()` from `@wadeck-app/dsl-ui`: `format(value, style?, part?)`, `exact(value)`, `relative(value)`, `weekdays(style?)`, `months(style?)`, `intl(options)`. |

- `value` is a `Date`, epoch milliseconds or ISO 8601 text. An empty `value` shows nothing; any other text that is not a date is shown as it came and reported once in the console.
- Chart axes: `weekdays('narrow')` gives seven names starting at the user's first day of the week; `intl(options)` is an `Intl.DateTimeFormat` with the user's language, time zone and hour cycle. Do not call `Intl` with an undefined language: that is the browser's, not the user's.
- `dsl-ui` is a shared singleton, so your bundle and the shell see the same formatter. `dslLib.shared` must ask `@wadeck-app/dsl-ui` at `2026.10.26-290` or later to use these.

### Providers and dependents

A module that `requires` another follows it:

| Event on provider `P` | Dependents (transitive) |
|---|---|
| Unregistered, unloaded, or ends up `failed` (an update failed after its teardown) | Unloaded, dependents before providers, teardown reason `dependency`. Each is recorded in `failed` with cause `requirement` and the message `required module "P" was unregistered: ...` / `required module "P" failed: ...`. Their registry entries are kept. |
| Updated and loaded | Each direct dependent is checked again with the load rules (version range, exposed slots, accepted root `$type`). An incompatible one is unloaded and failed with the exact problems (`... cannot stay loaded after "P" was updated to <v>`); a compatible one is not touched (no teardown, no setup). |
| Update refused by the pre-checks | Nothing: the old `P` and its dependents keep running. |
| Update that makes `P` require its own dependent | Refused (422, `require cycle (a -> b -> a)`). |

Auto-recovery: whenever a module becomes loaded (register, update, startup), the modules `failed` with cause `requirement` whose required modules are all loaded are loaded again, providers first, until nothing more loads. A retry that fails again updates the module's `failed` message. Failures of cause `error` (setup threw, invalid manifest) are never retried: register the module again. The affected ids are in `cascaded` and `recovered` of the HTTP answers.

Teardown order caveat: when an update of `P` fails after `P`'s own teardown, its dependents are torn down after `P`, not before.

### `$type` vocabulary

Every `$type` in your views comes from `@wadeck-app/dsl-ui`'s real component catalogue -- check
that package directly for what's available (`Badge`, `DataTable`, `StatTile`, and more). Views are
always DSL (consistency, and so modules stay easy for an AI agent to author). Prefer a generic
dsl-ui component; ship your own only when none can express the behaviour (a streaming log viewer,
say), through `dslLib` below.

## Shipping components (dsl-lib)

A module may bring its own business components. They are loaded into the shell at runtime, so no
shell rebuild is needed, and removed again when the module is unloaded or swapped.

You write the React source in the module, in `src/dsl-components/`; `package` builds it:

```
src/dsl-components/
  index.ts      default export = ComponentRegistryEntry[]
  style.css     precompiled CSS for those components (the shell does not scan your classes)
```

Declare it in the source manifest with the ranges you built against; `package` adds `entry` and `css`:

```json
"dslLib": { "shared": { "react": "^19", "react-router-dom": "^7", "@wadeck-app/dsl-ui": ">=2026.10.14-0" } }
```

`check` fails if `dslLib` is declared without `src/dsl-components/index.ts`, or if `src/dsl-components` has files and the manifest has no `dslLib` (they would not be packaged).

In the packaged manifest:

```json
"dslLib": {
  "entry": "./dsl-lib/entries.mjs",
  "css": "./dsl-lib/style.css",
  "shared": { "react": "^19", "react-router-dom": "^7", "@wadeck-app/dsl-ui": ">=2026.10.14-0" }
}
```

- `entry` and `css` must exist and resolve inside `dsl-lib/`. app-core serves them at
  `/api/modules/<id>/_lib/<file>?v=<version>-<mtime>-<size>`; `_lib` is reserved, so
  `registerRoute` refuses sub paths under it.
- Each entry is registered as `<moduleId>:<entry.name>`: a module registered as `orchestrator`
  with an entry named `JobCardGrid` is used in YAML as `$type: orchestrator:JobCardGrid`. Built-in
  dsl-ui components keep their plain names. A component that renders children by `$type` must use
  those exact names.
- Views of the module are not rendered until its components are loaded (the shell shows a loading
  state, or an alert with the reason if the import fails).
- Shared singletons: the shell provides `react`, `react/jsx-runtime`, `react-dom`,
  `react-dom/client`, `react-router-dom`, `@wadeck-app/dsl-ui` and `@wadeck-app/dsl-renderer` on
  `globalThis.__APP_CORE_SHARED__`, keyed by package name. `package` externalizes exactly those
  specifiers to that global (two Reacts, or two dsl-ui contexts, would break hooks, toasts and
  routing).
- `shared` declares the ranges you built against. At load, app-core checks them against the
  versions the shell was built with (`/build-info.json`); a mismatch, an unknown package or an
  invalid range makes the module fail with a message in `GET /api/modules` `failed`, and the running
  version is kept. If `build-info.json` is missing the check is skipped with a warning on stderr.
- The shell provides the router, `ToastProvider` and the theme tokens (use dsl-ui semantic classes,
  never raw colors). Use relative `/api/modules/<id>/...` URLs for your module's own endpoints.
- Build `src/dsl-components/style.css` with Tailwind using the dsl-ui preset AND its content globs, exactly like the
  shell: `presets: [dslUiPreset]` and `content: ['./src/**/*.{ts,tsx}', ...dslUiContent]` (both from
  `@wadeck-app/dsl-ui/tailwind-preset`). The shell injects your stylesheet after its own, and
  Tailwind orders utilities (`px-2` before `pl-7`) only inside one sheet. If yours lacks the
  dsl-ui classes but repeats a shorthand such as `.px-2`, it overrides the shell's longhand
  `.pl-7` on dsl-ui elements (the SearchBar icon then overlaps its placeholder). Measured: a
  module sheet without dsl-ui classes gives 8px instead of 28px; loading it before the shell's
  sheet fixes that element but breaks the module's own `px-2 pl-4` (8px instead of 16px); a sheet
  that includes the dsl-ui classes gives the right value for both. `package` copies the CSS you
  built as is; running Tailwind is your build step, not the CLI's.

Components run in the shell's origin with full DOM access: install only modules you trust.

## Naming

The package folder must be named `app-module-<name>` (e.g. `app-module-queue`), not
`<name>-app-module` and not a bare `app-module`. This is enforced by the `app-module/naming-convention`
`violations` rule in this repo (it flags any folder holding a `manifest.json`); `check` does not test the
folder name.

## Migrating an existing module to the new layout

For owners of a module written against the old layout (`api-backend/`, `dsl-frontend/`, `backendEntryPath` and `version` in the source manifest).

- [ ] Folder named `app-module-<name>`.
- [ ] Move the backend entry to `src/backend/index.ts` (default export `(ctx) => void`, unchanged). Helpers it imports go in `src/backend/` or, if components share them, `src/commons/`.
- [ ] Move views from `dsl-frontend/` to `src/dsl-views/`; change every path-type `view` to `./src/dsl-views/<file>.yaml`.
- [ ] Move dsl-lib React sources to `src/dsl-components/index.ts` (+ `style.css`, built with Tailwind before `package`). `.tsx` and `react` imports are allowed only there.
- [ ] `manifest.json`: add `id` (the id your daemon registers with); remove `version`, `backendEntryPath` and `dslLib.entry`/`css` (keep `dslLib.shared`).
- [ ] Slots other than `dashboard`, `nav`, `route`, `navbar`, `overlay` must be `<providerId>:<slot>`; declare the provider's slots in `expose`, and `requires` the provider in its consumers.
- [ ] Add `.gitignore` with `dist-module`; set `package.json` `"files": ["dist-module"]`; stop committing the former build output.
- [ ] Remove your own bundling script: `package` bundles the backend (CJS, including the `module.exports = module.exports.default` footer), the dsl-lib and the views.
- [ ] Replace raw `setInterval`/`setTimeout`/`addEventListener` in the backend by the `ctx` equivalents.
- [ ] Optional: move cleanup to a `teardown` hook and data upgrades to `migrate`; persistent files go under `ctx.dataDir`.
- [ ] CI: `BUNDLE_VERSION=<v> app-core-cli package .` before `npm publish`; the daemon registers `dist-module/manifest.json`, never the source manifest.
- [ ] `app-core-cli check .` until it prints `OK`, then `app-core-cli dev . --watch`.

## Troubleshooting

Texts are abridged to their stable part; `<...>` is filled in by the tool. `check` lists all its problems in one run, each with a `Fix:` line.

### `check` and `package`

| Message | Cause and fix |
|---|---|
| `folder "api-backend" is not allowed at the module root` | Old layout. Move sources into `src/{backend,dsl-views,dsl-components,commons}`. |
| `files are not allowed directly under src` / `"<x>" is not a known source folder` | Only the four folders exist under `src`. |
| `imports React ("react"), which is not allowed in src/backend` | React only in `src/dsl-components`. Same for `commons`. |
| `imports the Node builtin "<x>", which is not allowed in src/commons` | `commons` is shared with the browser; move that code to `src/backend`. |
| `src/backend must not import from src/dsl-components` (or the reverse) | Move the shared code to `src/commons`. |
| `the backend entry has no default export` | `src/backend/index.ts` needs `export default function (ctx) {...}`. |
| `Unrecognized key(s) in object: 'version', 'backendEntryPath'` | Source manifests hold only `id`, `extensionPoints`, `dslLib.shared`, `requires`, `expose`, `lifecycle`. |
| `referenced by manifest.json (extensionPoints[<n>]) but does not exist` | Create the view or fix its `./src/dsl-views/...` path. |
| `.gitignore: missing; dist-module must be gitignored` / `does not ignore dist-module` | Add the line `dist-module`. |
| `package.json: "files" is [...], but only dist-module may be published` | Set `"files": ["dist-module"]`. |
| `contributes to "<p>:<slot>" but "requires" does not list "<p>"` | Add `"requires": { "<p>": "^1.0.0" }`. |
| `no dependency provides module "<p>" (looked at ... (not installed))` | Add the provider to `dependencies`, install and build it, or pass `--link <package>=<folder>`. |
| `No version to stamp into the manifest` | `package` needs `--version <v>` or `BUNDLE_VERSION`. |
| `The output folder <dir> is not allowed` | `--out` must not be the module, a parent of it, or inside `src/`. |
| `<a> and <b> would both be emitted as <path>` | Two views would write the same output file; rename one. |
| `<step> failed:` then `file:line:col: <text>` lines | esbuild error in your source; a missing package usually needs `npm install` in the module folder. |
| `The packaged manifest's <field> "<x>" does not exist` | A path in the manifest points to something `package` did not write; fix the source path. |
| `--link "<x>" is not of the form <package>=<folder>` | Use `--link @acme/provider=../provider`. |
| `warning: <view>: <node> has a "children" key, which built-in components ignore ...` (`package`, `dev`), or a page or widget that renders blank with no error anywhere | Built-in containers read their child nodes from `items:`, not `children:` (checked in the dsl-ui catalogue: VerticalStack, HorizontalStack, Card, Section, PageSection, Collapsible, ActionBar, CardActions, DialogFooter, NavBar, ScrollArea, TableRowActions, ThemeScope, Dialog, Drawer, Popover, Tooltip, ToastProvider, RouterProvider, BulkActionsToolbar, ChipButton, DeleteButton). The renderer ignores unknown keys, so a wrong key renders an empty container silently. Rename `children:` to `items:`. |

### `dev`

| Message | Cause and fix |
|---|---|
| `<manifest> has no "id"` | Add `"id"` to the manifest. |
| `--id "<a>" differs from the "id": "<b>" declared in ...` | `--id` only asserts the manifest id; drop it or fix the manifest. |
| `is a source manifest (no backendEntryPath) but <dir> has no src/ folder` | Pass the source module folder, or a built `dist-module`. |
| `--watch needs a source module ... but <dir> is built output` | Pass the module folder, not `dist-module`. |
| `--poll only applies to --watch` | Add `--watch` or drop `--poll`. |
| `Module "<p>" (required by "<m>") has no built package to register` | Install the provider, build it with `package`, or pass `--link`. |
| `... is a source module in <dir> and has not been built, dev does not package dependencies` | Run `app-core-cli package <dir> --version <v>` for it, then `dev` again. |
| `Module require cycle: a -> b -> a` | Break the cycle in `requires`. |
| `module "<id>" failed to load: <reason>` | The reason is a server message, see the next table. |
| `--reset could not remove <dir>` | Stop whatever uses its files, or delete the folder by hand. |
| `--previous-version <v> is the version dev loads ... migrate would not run` | Pass another version. |
| `--previous-version needs a version` | Give a value, e.g. `--previous-version 1.0.0`. |
| `the server refused the update (HTTP <n>): ...` | A rebuild produced a manifest the server rejects; the previous version keeps serving unless the message says the module is failed. |

### Server: registration and load

These appear as the HTTP `error` of `register`/`update` and under `failed` in `GET /api/modules` (also on stderr at startup).

| Message | HTTP | Cause and fix |
|---|---|---|
| `Module registered as "<a>" but its manifest <path> declares "id": "<b>"` | 400 | Register under the manifest id, or change the manifest. |
| `module "<id>": the manifest <path> is invalid: <field>: <reason>` | 400 | Typically a source manifest was registered: register `dist-module/manifest.json`. `app-core-cli validate <path>` repeats the check. |
| `Invalid payload: source: Required. Fix the request body.` | 400 | Body must be `{ id, source: { type: "file", path } }`. |
| `Source type "npm" is not supported in v1` | 422 | Only `file` sources exist. |
| `module "<id>": the manifest <path> does not exist. Fix: register the absolute path of the packaged manifest ...` | 400 | Check the absolute path; `app-core-cli package` writes `dist-module/manifest.json`. |
| `module "<id>": the manifest <path> is not valid JSON (...)` | 400 | Fix the file or package again. |
| `the module's components were built for <pkg> "<range>" but the app-core shell provides <version> (<file>, built <date>, commit <sha>...)` | 422 | `code: "shared-version-mismatch"`. Compare the range of `dslLib.shared` with the version named. If the text ends with `the served shell looks stale`, the shell was built before the packages were updated: run `npm run build:full` in app-core and restart it, then register again. Otherwise rebuild the components against that version. The previous version keeps running (`retained`). `app-core-cli check` warns about this before you register. |
| `The registration is kept: "<id>" stays registered and failed, and is loaded automatically ...` | 422 | `retained: true`: provide the missing module; nothing else to do. |
| `Nothing was registered: "<id>" has no registry entry` / `... keeps serving and its registry entry is unchanged` | any | `retained: false`: fix the cause named above and register again. |
| `required module "<p>" was unregistered: register "<p>" again. ...` / `required module "<p>" failed: ...` | `failed` | A provider went away; the module loads again by itself when it is back (fix the provider if it failed). |
| `module "<id>" cannot stay loaded after "<p>" was updated to <v>: ...` | `failed` | The new provider no longer fits; the listed `Fix:` lines say how. |
| `requires "<p>", which requires "<id>" in turn: require cycle (...)` | 422 | Remove one of the `requires`. |
| `requires "<p>" "<range>": module "<p>" is not loaded` (or `... but version <v> of "<p>" is loaded`) | 422 | Register the provider first, or one whose version satisfies the range. |
| `... contributes to "<slot>" but ... does not expose the slot` / `... which accepts only: <types>` | 422 | Fix the slot id or the root `$type` of the view. |
| `module "<id>": cannot import backend entry <file> ...: The running version, if any, keeps serving.` | load | Syntax or import error in the bundle; rebuild. |
| `... must default-export a function (ctx) => void` | load | Wrong export. For a hand-made CJS bundle add `module.exports = module.exports.default;`. |
| `module "<id>": setup (...) failed: ... The module is failed and nothing it registered is left behind.` | load | Your setup threw; fix and register again. |
| `module "<id>": migrate (...) from <a> to <b> failed` | load | Fix the hook; it reruns on each load until it succeeds, so make it idempotent. |
| `timed out after <n> ms. A timed-out step cannot be cancelled` | load | Make the step faster or raise `APP_CORE_HOOK_TIMEOUT_MS`. |
| `its state file <file> ...` | load | Restore `{"version":"<last>"}` or delete the file (the next load is a first install). |
| `registerRoute: ... conflicts with the already registered ...` / `"<path>" is reserved` | load | Same method and shape twice, or a `/_lib` sub path. |
| `dslLib.shared["<pkg>"] is not provided by the app-core shell` / `the module's components were built for <pkg> "<range>" but the app-core shell provides <v>` | load | Declare only packages the shell shares; rebuild against its version. |
| `cannot verify dslLib.shared for ... (no build-info.json ...)` | warning on stderr | Run `npm run build:full` in the app-core repo; the ranges are not checked meanwhile. |
| `APP_CORE_HOOK_TIMEOUT_MS="<x>" is not a positive integer` | startup | Set a number of ms, or unset it. |
| `Bundled frontend not found at <dir>` | `serve` | Reinstall the CLI, or run `npm run build` in the repo. |

## Current limitations

Facts about the current platform, not promises.

| Limitation | Consequence |
|---|---|
| A timed-out promise cannot be cancelled in JavaScript (inherent) | A step reported as timed out may still be running in the background. |
| Module code can leak outside `ctx` (inherent: same process, decision 9) | A raw `setInterval`, global listener or open handle survives unload; `ctx` only clears what went through it. |
| No rollback after a teardown (inherent) | When the new code overwrote the same file, the old version cannot be restored: a failed update leaves the module `failed`. |
| `check` and `package` do not type-check | `check` parses syntax; esbuild strips types. Run `tsc --noEmit` yourself. |
| `dev` does not watch dependencies | Rebuild a dependency and restart `dev`. |
| A failed `dev` rebuild can leave `dist-module` incomplete | The next good rebuild restores it; the server keeps the previous version. |
| An update of `P` that fails after its teardown tears its dependents down after `P` | See Providers and dependents. |
